# Задание: автоматическое переобучение модели (BPMN)

> Статус: **черновая запись.** Источник: один слайд из презентации преподавателя
> («Оркестрация retraining в BPMN»). Полное ТЗ и презентацию пользователь пришлёт позже,
> после этого документ нужно уточнить и реализовать задание.

## Что нужно

Описать диаграммой BPMN и затем реализовать процесс **автоматического переобучения модели**.

## Процесс со слайда

| № | Элемент BPMN | Содержание |
|---|---|---|
| 01 | Start Event | запуск по расписанию или триггеру |
| 02 | Service Task | загрузка новых данных |
| 03 | Service Task | обучение модели |
| 04 | User Task | валидация |
| 05 | Gateway | условие: AUC > 0.8? |
| 06 | ветки шлюза | **Да** → деплой; **Нет** → уведомление + логирование |
| 07 | End | завершение «но с возвратом к мониторингу» (процесс замыкается на мониторинг) |

## Предварительные соображения (не часть ТЗ, мои предположения)

Что из существующего проекта может лечь на шаги процесса:

| Шаг | Что есть в проекте |
|---|---|
| 01 Start Event | расписание, например `schedule` в GitHub Actions или cron; ручной триггер |
| 02 Загрузка новых данных | `insurance download` (`data.py`, проверка SHA-256) |
| 03 Обучение | `insurance train` (`train.py`), метрики в `metrics.json` |
| 04 Валидация (User Task) | ручной просмотр метрик и отчёта; в проекте этого шага пока нет |
| 05 Шлюз AUC > 0.8 | сравнение `roc_auc` из `metrics.json` с порогом; порог вынести в конфиг |
| 06 Деплой / уведомление | деплоя нет (есть только `ModelBundle.save` и Docker-образ); уведомления и логирование нужно добавить |
| 07 Мониторинг | в проекте не реализован (дрейф данных, качество на новых данных) |

Замечания:
- Порог шлюза задан по **AUC**, а в проекте основная метрика F1. AUC уже считается (`roc_auc`), на
  выборке 3% он около 0.873 у лучшей модели, то есть порог 0.8 проходится.
- «Новые данные» в проекте сейчас один статичный файл, нужно решить, что считать новыми данными.

## Что уточнить, когда придёт полное ТЗ

- Нужна ли только диаграмма или ещё рабочая реализация, и в каком инструменте (Camunda, Airflow,
  GitHub Actions и т. д.).
- Какие данные считаются новыми и как задаётся триггер.
- Что именно означает «деплой» и «мониторинг» в рамках задания.
- Формат сдачи.
